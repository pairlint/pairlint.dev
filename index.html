Design token contrast linter

Contrast checks for your whole design system, not one color pair at a time.

pairlint checks color contrast against WCAG 2.2 for every text and background pair in your tokens, in every mode: light, dark, high contrast and every brand and theme combination. When a pair fails, it tells you which line to change and what to change it to.

The problem

You check one pair. You ship hundreds.

Contrast checkers test the two colors you paste in. A real design system has hundreds of text and background pairs, and every one of them changes in dark mode, in high contrast and in your second brand. Nobody pastes all of those in, so the failures ship.

A contrast checker

You paste in the muted text color and the surface it sits on, in the theme you happen to be looking at.

7.57:1. Looks fine.

Use cases

Built for the way design systems actually change

Adding a theme, launching a brand, reviewing a token change. These are the moments contrast breaks, so these are the moments pairlint is built for.

Design system teams

Add dark mode without guessing

Your light theme passed review years ago. Dark mode reuses the same token names with new values, and some of those values are a shade too close to the new surfaces. pairlint checks every pair in both themes and points at the exact token to change.

  • File, line and column for every failure
  • Suggests the nearest passing shade from your own scale, so the system stays intact
  • When no shade works, an exact new value with only the lightness changed

Multi-brand companies

Every brand, every theme, one run

Two brands and two themes are four products to check. Five brands with light, dark and high contrast are fifteen. Describe your brands and themes as groups and pairlint checks every combination on its own, up to 256 of them.

  • Brand × theme modes named like acme/dark
  • A theme can override a brand, the way your CSS does
  • Check a pair only where it applies, such as "modes": ["dark"]

Engineering and CI

Stop contrast regressions at the pull request

Run pairlint on every token change. It exits with code 1 when a pair fails, writes a Markdown summary for the pull request, and writes SARIF so failures show up as code scanning annotations on the token's own line.

  • Clear exit codes: 0 pass, 1 fail, 2 broken config
  • Markdown for PR comments and job summaries
  • SARIF 2.1.0 for GitHub code scanning
  • Baselines let you turn it on today and fail only on new problems

Designers and reviewers

A report designers can actually read

Not everyone reads terminal output. The HTML report is one self-contained page with color samples, ratios and a preview of each suggested fix, in light and dark themes. It has no scripts and loads nothing from the network, so you can attach it to a ticket or open it offline.

  • Swatches for every pair, failing and passing
  • Each fix shown next to the color it replaces
  • The report's own colors pass the WCAG AA contrast ratios, and a test checks that

What it checks

Exact answers, not close enough

A contrast tool that rounds is a contrast tool that lies. pairlint does the math the way the spec and the browser do it.

Reads the tokens you already have

W3C Design Tokens (DTCG), Tokens Studio, Style Dictionary 3 and CSS custom properties, including :root, theme selectors and @media (prefers-color-scheme). Aliases are followed, and several files merge per mode.

Points at the line to fix

Every failure comes with the file, line and column of the token to change, and the smallest change that passes: a shade from your own scale first, or an exact lightness-only value.

No rounding, ever

The report never rounds a failure up.

  • 4.49:1 needs 4.5:1Fails
  • 4.499:1 needs 4.5:1Fails
  • 4.50:1 needs 4.5:1Passes

Translucency done like a browser

A translucent foreground is blended over its background before measuring. A translucent background is blended over the mode's base color first. The result matches what people actually see.

Modern color spaces

Hex, rgb(), hsl(), oklch(), oklab() and Display P3. Colors outside sRGB are mapped with the CSS Color 4 gamut mapping algorithm, and pairlint tells you those results are approximate.

Baselines with an owner

Adopting on a big system? Record today's failures and fail only on new ones. Every accepted failure needs an owner and a reason, can expire on a date, and comes back as a failure when it does.

Reports

One check, a report for everyone

Pick a format with --format and write it anywhere with --output.

  • text

    For you in a terminal. Failures grouped by mode, with fixes and file locations.

  • json

    For scripts. Every result, ratio, color, suggestion and location, with a versioned schema.

  • sarif

    For GitHub code scanning. Failures show as annotations on the token's line in pull requests.

  • markdown

    For pull request comments and job summaries. A short summary and a table of fixes.

  • html

    For designers and stakeholders. One self-contained page with swatches, in light and dark.

  • GitHub annotations

    For workflow logs. Failures appear inline on the changed token files.

Security

Small enough to trust

A linter runs on every developer's laptop and in every CI job. It should not be able to do anything except read your tokens and print a report. pairlint is built that way on purpose.

CI checks the code for network, process and eval access on every change. Read the security policy.

  • Zero runtime dependenciesNothing else gets installed with it, so there is no dependency tree to audit.
  • No network accessIt makes no requests and works fully offline.
  • No install scriptsInstalling it runs nothing.
  • Reads only your project folderIt only opens files inside the folder that holds its config.
  • Never runs your codeToken files are parsed as data. JavaScript configs are never evaluated.
  • MIT licensedRead every line, fork it, ship it in your own tools.
